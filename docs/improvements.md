Security
The PBKDF2 key derivation is a reasonable choice, but you should consider upgrading to Argon2id (via argon2-cffi) for user credential hashing, as it's the current best-practice recommendation and resists GPU-based attacks better. More importantly, private key material derived from user credentials should be explicitly zeroed out in memory after each request — Python doesn't guarantee this automatically, so using memoryview wipes or a SecretStr pattern (via pydantic) is worth doing. Also, flask-limiter is listed in the stack but its scope isn't clearly defined — rate limiting should cover the /api/auth/login and /api/harvest/* endpoints specifically, not just globally.

Resilience
The four-pipeline transaction engine runs all four cryptographic paths concurrently, which is great for comparison — but if the liboqs C-extension throws a native exception on one pipeline (e.g. ML-KEM-1024 on a system missing AVX2 support), it could bring down the entire transaction rather than failing gracefully with a partial result. Each pipeline should be wrapped in independent try/except with a fallback result structure so a single algorithm failure doesn't block the COMMITTED state. For NeonDB production use, you'll also want to configure SQLAlchemy's pool_pre_ping=True and set explicit pool_size limits.

Observability
The current logging goes to ../logs/pytest.log (test-time) but there's no mention of structured runtime logging. Adding structlog for JSON-formatted logs with fields like user_id, algorithm, latency_ms, and transaction_id would make the audit trail directly queryable. Since the analytics dashboard already tracks latency percentiles, exposing a /metrics endpoint in Prometheus format (using prometheus-flask-exporter) would let this system plug into standard monitoring stacks for any production evaluator reviewing this as a PoC.

Scalability
The current NotificationService/EventBus pattern for SSE works well for a single-server setup, but if you were to run two Flask workers (e.g. under gunicorn with --workers 2), SSE events from one worker wouldn't reach clients connected to the other. Adding Redis pub/sub as the EventBus backend (with a feature flag to keep the in-process bus for development) would make this horizontally scalable without changing the service interface. Similarly, the Qiskit simulation in Phase 3 of HNDL can be slow — offloading it to a Celery task with a result callback would prevent it from blocking the Flask request thread.
PQC roadmap
The current implementation covers ML-KEM (key encapsulation) which is the right starting point, but a production quantum-safe banking system also needs post-quantum signatures for transaction signing. ML-DSA (FIPS 204, also via liboqs) is the natural complement to ML-KEM. Adding even a stub MLDSASigner class in crypto/pqc.py alongside your existing KEM methods would make the cryptographic story complete — RSA-PSS is currently used for signing but is equally vulnerable to Shor's algorithm as RSA-OAEP. This would also be a meaningful addition for the academic evaluation dimension of the project. A hybrid X25519 + ML-KEM key exchange (as recommended by NIST's migration guidance) would also be worth documenting as a future path.

Developer experience
The setup guide is comprehensive, but the liboqs C-library submodule dependency is the highest-friction part of onboarding — it requires a working C compiler and cmake, and will silently fail on some environments. A docker-compose.yml that pre-builds liboqs would eliminate this entirely and is essentially table stakes for a PoC that's going to be evaluated by others. Also worth adding: a contract test layer (e.g. using schemathesis against your OpenAPI spec, or just pytest fixtures that assert response shapes) so that frontend/backend integration breaks are caught at the API boundary rather than in the React components.
